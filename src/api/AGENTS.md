# src/api

HTTP route layer. Each file exports a single Elysia instance composed in `src/index.ts`.

## OVERVIEW
Route modules for the HTTP API. Static file serving is extracted to `static.ts`.
Key management is split across 3 sub-modules with a thin orchestrator in `keys.ts`.

## STRUCTURE
| File | Route(s) | Purpose |
|------|----------|---------|
| `suggest.ts` | `GET /suggest` | Main autocomplete (p95 < 50ms) |
| `address.ts` | `GET /address/:id` | Full record by `address_detail_pid` |
| `health.ts` | `GET /healthz`, `GET /readyz` | Liveness + readiness probes |
| `warmup.ts` | `POST /warmup` | 20 queries to load indexes into `shared_buffers` |
| `openapi.ts` | — | `@elysiajs/openapi` config (served at `/openapi`) |
| `static.ts` | 15+ routes | Static file serving: favicon, CSS, JS, HTML, tab fragments |
| `auth.ts` | — | Auth derive middleware (`authDerive` + `authPlugin`) |
| `stats.ts` | `GET /api/stats` | Public usage statistics |
| `keys.ts` | — | Orchestrator + shared helpers for key sub-modules |
| `keys-gen.ts` | `GET /api/config`, `POST /api/keys` | Key generation + Turnstile verification |
| `keys-mgmt.ts` | `POST /api/keys/manage`, `POST /api/keys/:prefix/revoke`, `GET /api/keys/:prefix/status` | Key management |
| `keys-recover.ts` | `POST /api/keys/recover/start`, `POST /api/keys/recover/verify`, `POST /api/keys/:prefix/verify` | DNS recovery + key verification |

## WHERE TO LOOK
| Task | Location |
|------|----------|
| Add endpoint | New file → `export const xxxRoute = new Elysia().get/post(...)` → register in `src/index.ts` via `.use(xxxRoute)` |
| Add static file route | `src/api/static.ts` |
| Modify key management | `src/api/keys*.ts` — gen, mgmt, and recover sub-modules |
| Add validation | Use Elysia `t` namespace — `t.String({ minLength, maxLength, pattern })` |
| Error handling | Throw `AppError(message, statusCode, code)` from `src/lib/errors.ts` |

## CONVENTIONS
- **Error handling**: ALL error responses SHALL be generated by `throw new AppError(message, statusCode, ERROR_CODES.X)`. Inline `set.status + return { error, code }` is forbidden — it bypasses the global handler and the `meta` envelope.
- **Response envelope**: Every response includes `meta: { took_ms, request_id, timestamp }`. Success fields are additive (backward-compatible). Error shape is `{ error, code, meta }`.
- Response schemas defined inline via `response: { 200: t.Object({...}) }`
- All error codes are uppercase snake: `INTERNAL_ERROR`, `VALIDATION_ERROR`, etc.
- Static files use a shared `serveStatic()` helper in `static.ts`
- Key sub-modules import shared helpers (`validateDomain`, rate limiters) from `keys.ts`
- SQL queries are imported from `src/sql/` modules (not written inline)

## ANTI-PATTERNS
- **NEVER** write raw SQL inline in route handlers — use `src/sql/` modules instead
- **NEVER** cache paginated results — only `offset === 0` is cached
- **NEVER** include trigram queries in `/warmup`
- **NEVER** read `process.env` directly in route code — use `getConfig()`
- **NEVER** extend `keys.ts` with new routes — add them to the appropriate sub-module

## GOTCHAS
- `static.ts` avoids duplication via the `serveStatic(path, contentType)` helper
- `keys.ts` is both orchestrator (composes sub-routes) and shared-helper module
- Rate limit state is in-memory: `keygenIpMap`, `verifyIpMap` — lost on restart
- Recovery sessions are in-memory: `recoverySessions` Map — expires after 5 min
