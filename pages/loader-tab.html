📦 G‑NAF Loader Pipeline

Every G‑NAF release (quarterly: Feb · May · Aug · Nov) must be loaded from raw PSV files into PostgreSQL. The loader at scripts/load.ts orchestrates 9 parallel workers (one per AU state/territory) through a 7‑phase pipeline. Total time for 16M addresses: ~9.5 min (570s) on a MacBook Pro M5 Pro (48GB) · macOS 26.5.1 · Bun 1.3.14 · Postgres 18-bookworm (Docker) · 16GB container limit. Uses COPY FROM STDIN streaming via the postgres package (peak memory ~900MB).

📐 Architecture

The loader runs as a single orchestrator process that spawns 9 parallel worker processes, then runs sequential post-processing steps on the database. All data flows from PSV files → staging tables → materialized view.

Step 1
Orchestrator (scripts/load.ts) —  drops staging indexes, disables autovacuum, spawns 9 worker processes, then waits for all to complete.
Step 2
9 workers (Bun.spawn("load-worker.ts")) —  one per state, each reads 5 PSV files and pipes them into COPY FROM STDIN on 5 staging tables (staging_state, staging_locality, staging_street_locality, staging_address_detail, staging_address_geocode).
Step 3
Post‑worker — denormalization UPDATE, staging index recreation, pg_prewarm, pre‑filter DELETE of retired/alias rows.
Step 4
MV REFRESH — drops indexes, runs REFRESH MATERIALIZED VIEW, then recreates 10 indexes in parallel (6 connections). pg_prewarm indexes, re‑enable autovacuum.
Step 5
Done — address_search_mv is populated with 16M rows and all 8 indexes are hot in shared_buffers. The API is ready to serve queries.

💾 Memory & Disk

The loader is designed to keep peak container memory under 1GB during the COPY phase. COPY FROM STDIN (via the postgres package) streams data directly from file to heap without buffering in shared_buffers — peak ~900MB for 9 concurrent workers. The MV (3.3GB heap) and its 10 indexes (12GB) occupy ~16GB on disk, plus ~5GB for WAL and ~5GB for the G-NAF PSV files = ~27GB total volume. Measured live on the deployed container.

⚙️ Key Optimizations

Eight design decisions that make the loader fast. These are independent of the pipeline order — each optimization targets a specific bottleneck (memory, WAL, index maintenance, cache warmup).

COPY
COPY FROM STDIN — streams data directly to the PostgreSQL heap without building JS-side parameter arrays or dirtying shared_buffers. 200‑500K rows/sec per connection. Reduces peak memory 10‑25× vs bulk INSERT.
UNLOGGED
UNLOGGED staging tables — skip WAL generation during the load. Makes COPY 3× faster. Data is destroyed on crash, but since we always re‑load from PSV files, that is acceptable.
Parallel
9 parallel workers — one Bun.spawn per state. Each loads its own file, no cross‑worker state. The orchestrator waits for all 9 via Promise.all(proc.exited).
Denorm
Orchestrator‑level denormalization — a single 4‑table JOIN UPDATE after all workers finish. Populates _dn columns (street name, locality, state) so the MV REFRESH can read them directly instead of JOINing 4 tables.
Pre‑filter
Pre‑filter retired/alias rows — DELETE from staging before REFRESH reduces MV row count ~5‑10% and eliminates the per‑row WHERE clause during REFRESH. Also deletes matching geocode rows to satisfy FK constraint.
Drop idx
Drop MV indexes before REFRESH — the 8 indexes would otherwise be maintained during the 16M‑row INSERT. Dropping first lets REFRESH just write sequentially, then indexes are recreated in parallel (6 connections) for 2× faster index build vs serial.
GIN
GIN trigram with fastupdate=off — the GIN index on search_text_expanded uses the pending list by default. Disabling it improves Tier2/Tier4 query latency 20‑30% at the cost of slightly slower index builds.
Prewarm
Post‑load pg_prewarm — loads the 6 most‑used MV indexes into shared_buffers so the first user query does not hit cold disk reads. Skips the GIN FTS index (no query tier uses it).

📋 Quarterly Refresh Checklist

G‑NAF is published ~4×/year (Feb, May, Aug, Nov). Each refresh requires a full reload — the staging tables are TRUNCATE'd and re‑populated from the new PSV files. The loader is idempotent: it checks pg_matviews.ispopulated and information_schema.tables to skip schema setup if already applied, so a regular refresh is just point the loader at new PSVs and re-run.
# 1. Download the new G‑NAF release from data.gov.au
# 2. Point GNAF_DATA_DIR at the new PSV files
export GNAF_DATA_DIR=/path/to/G-NAF\ MAY\ 2026/Standard
# 3. Run the loader (~10 min for 16M rows).
# Schema is skipped (tables exist), staging is TRUNCATEd,
# workers re-COPY, MV REFRESHes, indexes rebuild.
docker compose run --rm api bun run scripts/load.ts
# 4. Restart the API
docker compose restart api
# 5. Warm the cache
curl -X POST http://localhost:8000/warmup
# 6. Verify
bun run benchmark/bench.ts
# Only needed for schema changes or first deploy:
docker compose down -v && docker compose up -d db

📊 Benchmark

Full workload benchmark: 1000 mixed queries (31 distinct shapes) against the freshly‑loaded API. Warm cache uses the in‑process LRU (30s TTL, 1000 entries) — repeated queries hit the cache and return in <1ms. Cold cache appends &no_cache=1 so every request is a real DB query. The target is p95 < 50ms.
