📏 How the numbers above are measured
Two separate measurements — they answer different questions:
server took_ms = time spent inside the route handler (DB query + JSON encode) client HTTP = full round-trip the browser sees (send + server + receive) benchmark = end-to-end round-trip, 1000 mixed queries, ?no_cache=1
  • server took_ms (in the response body): measured from performance.now() at the start of the route handler (src/api/suggest.ts:66) to the return. Excludes network and middleware. Always present, integer ms.
  • client HTTP (the meta line in the test UI): measured around await fetch() in pages/assets/suggest.js:106. await fetch() resolves when response headers are received — it does not include resp.json() parse time. Includes network round trip + server processing + headers-back.
  • benchmark (benchmark/bench.ts): same performance.now()-around-fetch pattern, but appends &no_cache=1 so the in-process LRU is bypassed. 1000 iterations cycling 31 distinct query shapes, 7-tier mix.

Why the site can feel slower than the benchmark: the benchmark uses ?no_cache=1, so every request is a real DB query (worst case). The test UI does not pass no_cache, so the server-side LRU returns cached results in <1ms for repeated queries. The first click on a tier button is the slow one (cache miss); subsequent clicks are <1ms. Slower queries like tier0_number (e.g. "12 VIC", p95 ≈ 69ms) are weighted by ~3% in the mixed benchmark, so they barely move the headline p95 even though they take longer individually.

Full workload benchmark (1000 mixed queries, 31 distinct query shapes, cold cache): p50 7.0ms · p95 26.4ms · p99 28.3ms · avg 9.6ms · max 34.0ms. The tier1 prefix requirement was lowered to 1 char (was 3), so most queries including "y st"/"pi st" and short strings like "ab cd sydney" now hit the fast btree index instead of the slow GIN trigram index. The address normalizer rejects 3+ consecutive number queries early, preventing slow trigram fallback for random digit input. Repeated queries are <1ms with the in-process LRU. Run bun run benchmark/bench.ts to reproduce.

🔄 Query Router

Every query goes through a hardcoded decision tree that picks the cheapest index. The router checks each condition in order and returns the first match:

tier0_locality
State + locality prefix — btree on (state, locality_lc text_pattern_ops). Fastest tier: triggers when the query has a state filter and the last token is alphabetic (≥2 chars) and not a street type. The locality prefix is used as a LIKE filter, not just a boost. E.g. "syd nsw" finds all localities starting with "syd" in NSW. p50: 4.4ms · p95: 7.6ms · Index: idx_mv_tier0_state_locality
tier1
Street name prefix — btree on (street_lc text_pattern_ops, confidence_norm DESC). The primary workhorse tier. Fires when the query has an alphabetic token ≥1 char that looks like a street name (not a state or flat type). STREET_TYPE_LC names like "avenue"/"close"/"lane" are accepted (some AU streets are named after street types). The street number, flat number, locality, and street type are all used as ORDER BY boosts (not filters) — the most specific boost wins the top slot. p50: 8.2ms · p95: 10.5ms · Index: idx_mv_tier1_street_prefix
tier0
State + postcode equality — btree composite index on (state, postcode). Only fires when the query has both a state filter and a postcode filter (e.g. "sydney nsw 2000" or ?state=NSW&postcode=2000). Avoids redundant full-address lookups via the hasFullAddress gate. p50: 9.8ms · p95: 23.1ms · Index: idx_mv_tier0_state_postcode
postcode
Postcode prefix match — btree on (postcode text_pattern_ops). Triggers when the entire query is a 2-4 digit numeric string (e.g. "2000" or "20"). For 4-digit exact postcodes uses equality (index Cond, no recheck). For shorter prefixes uses a LIKE range scan. p50: 14.4ms · p95: 23.4ms · Index: idx_mv_postcode_prefix
tier4
Multi-word GIN fallback — GIN trigram on street_lc and locality_lc (individual columns, not the full address string). Rarely fires — the tier1 prefix check accepts 1-char prefixes, plus non-alpha prefixes like "a1"/"b1" now route to tier1 via the /^[a-z]/ regex fix. Address normalizer short-circuits 3+ consecutive number queries before they reach this tier. Uses a LIMIT 8000 subquery before DISTINCT ON (display) to bound the sort cost. p50: 16.6ms · p95: 19.3ms · Indexes: idx_mv_tier4_street_trgm + idx_mv_tier4_locality_trgm
tier2
Single-word trigram fallback — GIN trigram on search_text_expanded. For single-word queries with no matching street/locality prefix. Most single-word queries are now caught by tier1 (any prefix ≥1 char). p50: 6.8ms · p95: 17.8ms · Index: idx_mv_tier2_trgm
tier0_number
State + street number — btree on (state, number_first). Fires when the query has both a state filter and a leading numeric token (e.g. "12 vic" or ?state=VIC&q=12+main+st"). Skips full addresses (5+ tokens with a street name) — those need tier 1's per-street-number boost logic instead. p50: 30.7ms · p95: 68.6ms · Index: idx_mv_tier0_number_first
✏️ Typo Corrector before DB

An in-memory corrector rewrites typos before routing, so the DB never sees a misspelt street, suburb, or state:

street
700K distinct street names — SymSpell deletion index. For each name, pre-compute all single-character-deletion variants (~10 per name). To correct a query, generate its own deletions and intersect with the index. Matching names are the closest candidates within edit distance 1-2, scored by shared-deletion count with frequency as a tie-breaker. Catches 1-char insertions ("gresfodr" → "gresford"), deletions ("gresfrod" → "gresford"), and substitutions ("gresfird" → "gresford"). Memory: ~200MB. Threshold: ≥4 chars (≤3 is too short for reliable correction).
locality
16K distinct locality (suburb) names — SymSpell deletion index. Same algorithm as the street corrector but a separate dictionary loaded from SELECT locality_lc, COUNT(*) FROM address_search_mv GROUP BY locality_lc. When the tokenizer's localityPrefix is ≥3 chars and not in the dictionary, the corrector finds the closest in-dictionary match. Corrects suburb typos like "wntirna" → "wantirna". Threshold is 3 chars (vs 4 for streets) because short locality names like "syd"/"mel" are common and worth correcting. Memory: ~10MB (40× smaller than the street dictionary).
state
9 AU state/territory codes — closed-set Levenshtein-1. No dictionary needed — just standard Levenshtein distance against the 9 valid codes: ACT, NSW, NT, QLD, SA, TAS, VIC, WA, OT. Conservative: only returns a correction when exactly one valid state has distance ≤1 from the input token. This avoids guessing when multiple states are close (e.g. "ns" is at distance 1 from NSW, NT, and SA — all three are rejected). Applies in two places: (1) query-token state detection via detectStateFilter() — e.g. "sydney nswq" corrects "nswq" → "NSW", and (2) the explicit ?state= query param — e.g. ?state=nswq silently corrects and returns state_corrected_from: "nswq". Invalid params with no 1-edit candidate get HTTP 400. Negative examples: "nz" → "NT" (unique, distance 1), "ns" → rejected (3 candidates), "xyz" → rejected (no candidate within 1).

Corrector response fields: corrected_from · locality_corrected_from · state_corrected_from

Startup: ~3s · Memory: ~210MB · No-op if DB is unreachable

Within each tier, results are ranked by:
number_first = X DESC → exact X in display → flat number in display → street_type match → display LIKE 'unit %' → confidence DESC → display

📖 Why This Project Exists

Geoscape Australia publishes G-NAF — the authoritative list of every address in Australia — as a free download. It's a 16-million-row dataset updated quarterly. Building a fast autocomplete service on top of it is harder than it looks.

The problem. The official G-NAF reference schema (create_tables_ansi.sql + address_view.sql) is designed for offline analytical use — 30+ normalized tables, a 12-table JOIN view, and no indexes. A query like "1090 centre rd oakleigh south vic 3167" would take seconds because the database has to re-evaluate the entire 16M-row view every time, with no typo tolerance, no abbreviation matching, and no autocomplete-specific shortcuts.
Most address-lookup services cost money. Google Places, Mapbox Search, SmartyStreets, Loqate, what3words — all charge per-request or per-month once you exceed the free tier. A mid-traffic Australian site can rack up hundreds to thousands of dollars a month. This project exists because G-NAF is free public data (CC BY 4.0) and deserves a free, self-hostable, production-quality front-end. You pay for the Postgres box; you don't pay per keystroke.

Our solution. A self-contained service that loads G-NAF, builds a single optimized materialized view, and routes every query to the cheapest index — typically in under 5 ms. The trade-off is deliberately narrow: we don't try to be a general-purpose G-NAF database, just the fastest possible address-look-up endpoint.

⚖️ Schema Design: Original G-NAF vs This Project

The official G-NAF distribution ships SQL scripts to build a full normalized database (create_tables_ansi.sql, ~333 lines) and a flat view (address_view.sql, 74 lines). Our approach replaces those with a 5-table staging layer plus a single optimized materialized view. Both are valid; they serve different goals.

🟡 Original G-NAF

General-purpose normalized database
30+ tables · 638 lines of SQL · plain VIEW · no indexes on read target

PROS
  • Complete schema — covers mesh blocks, aliases, address sites, audit fields
  • Proper normalization (3NF, PKs, FKs, lookup tables)
  • Generic — answers any address question (counts, geocoding, joins)
  • Portable ANSI SQL — works on any RDBMS
  • No dependency on application code
  • Always-fresh data (it's a VIEW, not a snapshot)
CONS
  • No indexes on the read target — each query re-evaluates the view
  • 12-table JOIN runs at query time, every time
  • No display formatting — clients assemble the address string themselves
  • No typo tolerance — "sydne" finds nothing
  • No abbreviation matching — "ST" and "STREET" don't cross-match
  • Filter is minimal (excludes CONFIDENCE = -1 only)
  • Typical query time: seconds

🟢 This Project

Single-purpose autocomplete service
5 staging tables + 1 materialized VIEW · 10 indexes · in-process LRU cache

PROS
  • Sub-50ms p95 — measured 26.4ms p95 across 1000 mixed queries (cold cache)
  • Pre-computed display string — no runtime formatting
  • Pre-computed search_text_expanded with abbreviation expansion
  • 10 indexes picked for specific query shapes (state+postcode, number+state, locality+state, street prefix, trigram, FTS, street/locality GIN)
  • Smart 7-tier router — picks the cheapest index per query
  • Typo-tolerant (GIN trigram, similarity threshold)
  • "MAIN ST" matches "MAIN STREET" automatically
  • Aggressive filter — excludes retired + alias addresses
  • In-process LRU cache — repeated queries return in <1ms
  • In-memory Street+Locality+State corrector (SymSpell + Levenshtein-1, ~210MB, ~3s startup)
CONS
  • Single-purpose — can't answer mesh-block or alias questions
  • Audit fields dropped (date_created, legal_parcel_id, …)
  • No lookup tables — type names are hardcoded abbreviations in the MV DDL
  • Postgres-specific (pg_trgm, GIN, MV, custom postgresql.conf)
  • Materialized view is stale between refreshes (typically weekly)
  • Refresh cost: ~10 min for 16M rows on first load
  • Returns raw codes (U, not UNIT) — client maps them

When to use which. Need sub-50ms autocomplete at scale, with typos and abbreviations handled? Use this. Need mesh-block joins, ad-hoc analytics, audit history, or a portable schema? Use the original G-NAF scripts.

Best of both worlds. The two are not mutually exclusive. The original schema can be the source of truth (auditable, complete), and our materialized view can be a denormalized projection refreshed on top of it — you get full auditability and sub-50ms reads.
